# File storage security review (recordings and lead documents)

Reviewed 31 Oct 2026. Code:
- `src/server/storage/local.ts`, `src/server/storage/range.ts`
- `src/modules/files/lead-files.ts`
- `src/modules/recordings/*`, `src/modules/documents/*`
- `src/app/api/v1/leads/[id]/recordings`, `/documents`
- `src/app/api/v1/recordings/[id]`, `/documents/[id]`

## Checks

| Area | Finding | Evidence |
|---|---|---|
| Size limits | Recordings 25 MB and documents 10 MB, checked three times: declared `Content-Length` before the body is read (a request with no length is refused), the `File` size, then the byte length. | `recordings.test.ts`, `documents.test.ts` (max size accepted, max + 1 refused) |
| Content checks | The leading bytes must match the extension: MP3, M4A, AAC, OGG, WAV; PDF, JPEG, PNG; DOCX / XLSX must be OOXML packages with the right main part. HTML, executables, AMR, plain ZIP and ODT are refused; so are a WAV named `.mp3`, PNG named `.pdf` and DOCX named `.xlsx`. | Unit and integration tests |
| File names | Base name only, control characters removed, at most 200 characters. `Content-Disposition` has an ASCII fallback (quotes and backslashes replaced) plus RFC 5987 UTF-8, so the header can't be injected. | `recordings-rules.test.ts`; browser: an en dash name downloaded correctly |
| Private storage | Files sit under `FILE_STORAGE_DIR` (default `./storage`, git-ignored), never under `public/`; a folder inside `public/` is refused. Files are created with mode 600, written under a temp name and renamed, never overwritten (`wx`). | `local.ts` |
| Unauthorised download | Every read goes through `openLeadFile`: the role must be allowed to view leads (HR / accountant 403) and the lead must be in the user's scope (otherwise 404). Deleted leads count as not found. Responses are `private, no-store`, `nosniff`, sandbox CSP. Images open inline; PDF and Office files always download, so the browser never runs active content. | Integration tests for all six roles; browser checks |
| Path traversal | Storage keys are generated by the server (`<folder>/YYYY/MM/<uuid>.<ext>`) and validated with a strict pattern before any filesystem call; the resolved path must stay inside the root. Ids in URLs are UUID-checked. | `recordings-rules.test.ts` ("storage keys") |
| File type and ownership | A recording id can't be read through the documents route and the reverse (the kind is part of the lookup). Access always follows the file's own lead. | `documents.test.ts`, `workflows.test.ts` |
| Streaming and ranges | Recordings support `Range` (`bytes=a-b`, `a-`, `-n`); unsatisfiable or multi-range requests get 416 with `Content-Range: */size`. A file missing on disk gives 404 "file not found". | `recordings-rules.test.ts`; browser: 206 / 416 checked |
| **Fixed in this review** | The upload routes read the request body before checking lead access, so a user without access could make the server parse up to 25 MB before getting 404. **Lead access and the booked rule are now checked before the body is read.** | Route code; browser check: an out-of-scope agent gets 404 without the upload |
| Persistent storage | Production must set `FILE_STORAGE_DIR` to a persistent volume (`DEPLOYMENT_PROXY.md` §9). **Added:** a one-time server warning when production runs without it. | `local.ts` |
| Backups | Files are **not** in the database backup. Back up `FILE_STORAGE_DIR` with the nightly `pg_dump` and restore both together (`DEPLOYMENT_PROXY.md` §9, `SECURITY_AND_PRIVACY.md` §9). | Docs |

## Residual risks (not fixed: need a decision or the hosting environment)

Items 1–3 were reviewed again on 31 Oct 2026 (Playwright round). No cleanup, deletion or retention behaviour was added; the controls below are recommendations for the deployment.

### 1. Orphaned files after interrupted uploads

**How an orphan can arise.**
- **A browser that disconnects mid-upload** leaves nothing behind. The route reads the whole body with `req.formData()` before anything is written, so an aborted request fails before `putObject`.
- **A database failure after the write** leaves nothing behind either. `saveLeadFile` removes the file if the transaction throws.
- **A process crash or kill** can leave a file:
  - between `putObject` and the commit, the file `<folder>/YYYY/MM/<uuid>.<ext>` has no `files` row;
  - during `writeFile`, a `<uuid>.<ext>.part` file is left.
- **A failed `removeObject`** after a rollback (e.g. a disk error) leaves the file in place.

**Impact.** An orphan cannot be downloaded: every read starts from a `files` row checked against the user's lead access. It only uses disk space, and it is personal data with no owner record, so it matters for privacy and retention. Expect it to be rare: only a crash in a window of milliseconds produces one.

**Recommended production controls (no deletion).**
- Run the app under a supervisor that stops it gracefully (`SIGTERM`, then a delay) so in-flight requests finish: Docker `stop_grace_period: 30s`, or systemd `TimeoutStopSec=30`.
- Monitor free space on the `FILE_STORAGE_DIR` volume and alert at 80%.
- **Periodic read-only reconciliation**, done manually or by a script reviewed with the client, which reports:
  - files under `FILE_STORAGE_DIR` that have no `files.storage_key`;
  - any `*.part` files;
  - `files` rows whose file is missing.

  It must only *report*. Removing anything needs the client's written deletion and retention policy, the same rule as sign-in log retention.
- Back up `FILE_STORAGE_DIR` with the database (see Backups above), so a reconciliation decision can always be reversed.

### 2. No malware scanning

**Current mitigations.**
- Strict allow-list with content signature checks (above).
- No executable, HTML, SVG or archive formats.
- PDF and Office files are always served as downloads. Only JPEG and PNG open inline, under `sandbox` CSP and `nosniff`.
- Nothing is ever executed or parsed server-side beyond the leading bytes.
- Uploads require an authenticated staff account with edit rights on the lead.

**What remains.**
- A malicious PDF, or a DOCX / XLSX with an exploit or embedded object, could be uploaded by a compromised staff account and opened by a colleague's desktop software.
- `.docm` / `.xlsm` names are refused. The content check does not inspect OOXML parts beyond the main part, so a renamed macro-enabled package is not detected. Office still refuses to run macros from a `.docx` / `.xlsx` extension.

**Recommended production controls.**
- Run **ClamAV** (`clamd`) on the server and scan the `FILE_STORAGE_DIR` volume daily with `clamdscan --no-summary --infected`, in **report-only** mode (no `--remove` or `--move`). Alert the admins on any hit.
- Inline scanning before `putObject` (clamd `INSTREAM`) is the stronger option. It needs a decision on behaviour when the scanner is down: refuse uploads, or accept and flag them. That is the client's decision, so it is not implemented.
- Keep endpoint protection (Defender or similar) on the staff computers and phones that open downloaded documents.

### 3. No upload rate limiting

**Current bounds.**
- Uploads need a signed-in user with lead edit rights (agents on their own leads, managers on their team's leads, admins).
- Each request is size-capped before the body is read (25 MB recordings, 10 MB documents).
- Every upload writes an audit row with size and SHA-256 hash (`lead.recording_upload`, `lead.document_upload`), so abuse is traceable to an account.

**What remains.** A compromised or misused account can fill the disk by repeated uploads. There is no per-user quota or request rate limit.

**Recommended production controls.**
- **Proxy-level rate limit** on `POST /api/v1/leads/*/recordings` and `POST /api/v1/leads/*/documents`, for example 30 uploads per minute per client IP:
  - nginx: `limit_req_zone` / `limit_req`;
  - Caddy: the `caddy-ratelimit` module, which needs a custom Caddy build.
- **Proxy body cap** just above the app limit, so oversized bodies are refused before reaching Node:
  - Caddy: `request_body { max_size 26MB }`;
  - nginx: `client_max_body_size 26m`.
- **Disk monitoring and alerting** on the storage volume (as in item 1).
- **Audit review.** A weekly query of `audit_logs` for `lead.%_upload` grouped by actor shows unusual volume.
- An in-app per-user quota or limit (the existing `RATE_LIMITED` / 429 error is ready for it) needs client numbers: uploads per hour and total storage per user. Not implemented.

### 4. Storage location
Local disk only. S3-compatible storage needs the client's provider and credentials.

### 5. Deletion, replacement and retention
Deleting, replacing or setting retention for recordings and documents is not implemented; it waits for the client's rules.
